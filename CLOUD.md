# Future Google Cloud setup

1. **VM and HTTPS.** Serve `dist/ecommerce-demo/browser` on the public web VM. Configure the web server to fall back to `index.html` for Angular routes. Use a domain and TLS certificate, and reverse proxy `/api/**` to the HTTPS API Gateway hostname while preserving the path, query string, and cookie headers. Angular already uses relative URLs. Enable `COOKIE_SECURE=true` and test login and uploads through the HTTPS hostname.
2. **Gateway and function.** Register the exported Express app in `server/app.ts` as the HTTP handler with the Node.js Functions Framework. Keep `server/main.ts` as the local listener. Adapt multipart parsing to the function runtime's request body handling. Describe API routes in the gateway's OpenAPI configuration and configure backend path forwarding and the ID token audience for the function URL. For a current Cloud Run function, grant the gateway config's service account `roles/run.invoker` on the backing Cloud Run service. Keep IAM invocation required and use an ingress setting that admits requests from the gateway. The gateway's ID token authorizes infrastructure invocation. The app separately checks the shopper's session cookie and record ownership. [Backend authentication](https://docs.cloud.google.com/api-gateway/docs/securing-backend-services) · [Function invocation](https://docs.cloud.google.com/functions/docs/securing/authenticating) · [Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress)
3. **Private SQL connectivity.** Configure Direct VPC egress where supported by the deployment path, or a Serverless VPC Access connector, to reach the VPC with connectivity to the Cloud SQL private address. For direct PostgreSQL connections set `PGHOST` to that address and use port 5432 with the instance's TLS requirements. Cloud Run and API Gateway are managed services. The Cloud Run VPC connection is an egress path, and Cloud SQL private services access uses an allocated range for the service producer network. [Cloud SQL from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run) · [Direct VPC egress](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc) · [Private services access](https://docs.cloud.google.com/sql/docs/postgres/configure-private-ip)
4. **Credentials and photos.** Inject database credentials from Secret Manager into the function environment using a dedicated runtime identity with access to those secrets. Replace `server/photos.ts` and its static photo mounts with a private Cloud Storage bucket adapter. Give the runtime only the object permissions it needs. Keep storage keys in PostgreSQL and serve photo bytes through the API. [Cloud Run secrets](https://docs.cloud.google.com/run/docs/configuring/services/secrets) · [Cloud Storage IAM](https://docs.cloud.google.com/storage/docs/access-control/iam)
5. **Shared database.** Apply the schema in the existing database. Create only this application's quoted `"AH_..."` objects, leave all other student objects and data untouched, and give the runtime role access to this project's tables. Use demo seed accounts only if the shared environment is explicitly intended for classroom demos.
